# src/app/admin (the admin pages)

Admin-only work (things shared with every teacher, managing teachers) lives here, not in the editor.

- `layout.tsx` checks `getAccount().isAdmin` and shows "page not found" to everyone else, plus the header and the
  left menu (`AdminMenu.tsx`: the list of pages). A new admin page = a folder here + a line in `AdminMenu`.
- The admin pages use the full screen width. From `lg` the menu is a column on the left (it stays in place as
  you scroll); below that it is one row above the page that scrolls sideways. The menu has Overview on top, then groups, each a card with its label in violet: **Waiting for you** (Under review, Submissions, Reports), **Library**
  (Presentations, Photos, Photo cleanup, Data check), **People** (Teachers, Editors, Safety), and Admin log, Maintenance and Announcements on their own. The Waiting for you
  items show a yellow count pill when something waits. The numbers come from `getTodoCounts` (`todoCounts.ts`: the
  `admin_todo_counts` rpc wrapped in React `cache`, so the layout and the page share one call per request).
  `layout.tsx` passes them to `AdminMenu` (if the call fails, no pills); Overview's "Waiting for you" and the
  Presentations page's "Under review (N)" and "Submissions (N)" show the same numbers. Under review counts the rounds
  waiting for an admin (submitted), the ones the Under review list marks "Waiting for you", not the ones still being
  reviewed.
- The database still refuses non-admins on its own; the layout check only hides the pages.
- Super admin vs plain admins (root `CLAUDE.md`, "Super Admin"): `AdminMenu` items with `superOnly` (Teachers,
  Safety, Photo cleanup, Admin log, Data check, Maintenance, Announcements) show only for the super admin; those pages and their actions check `isSuperAdmin`.
  Admin → Photos shows a plain admin only their own photos (`uploaded_by`) and hides Categories. `setEditor`: only
  the super admin gives the role (never to an admin or a banned teacher); any admin takes it away (Admin → Editors
  uses it). `setShared` changes only a plain admin's own QuizMatter presentations (the super admin: any).
  `deleteReportedPresentation` deletes only a reported or hidden one. The database holds the same limits
  (`20261210000100_plain_admin_limits.sql`, root `CLAUDE.md` "Super Admin"), so these checks are only the first line.

## The pages

| Menu | Folder | What it does |
|---|---|---|
| Overview | `page.tsx`, `OverviewCharts.tsx`, `TeacherBreakdown.tsx` | The first page. What waits for you (the To do counts, linked), then bars per day for the last 7 / 30 / 90 days (`?days=`) from the `admin_overview` rpc (reads `activity_events` and the real tables; the people charts, the logins, signups, pauses and bans, come back only for the super admin). A chart that counts only rows still there (deleted presentations, unpublished copies, deleted accounts, each presentation's latest submission or review round) says so in its note under the bars. Reviews submitted counts each round on the day it was first submitted, so a sent-back round still counts (`first_submitted_at`, `20261210000500_admin_overview_counts.sql`). Then "Teachers": three cards of counts, no names (`TeacherBreakdown.tsx`, from the `admin_teacher_breakdown` rpc, any admin): by province (the 10 biggest, then "Others"), by age group (18–24 … 55+, from the birthday on today's Philippine date) and by gender, each with "Not given" last. The super admin also sees the latest admin actions |
| Photos | `photos/` (`page.tsx`, `AdminPhotos.tsx`, `photoSearch.ts`) | Shared photo library and its categories. Editors' uploads show as **Waiting** (pill + filter) until a live QuizMatter presentation uses them; editable like the rest. | ↳ Submissions | `presentations/submissions/` | Editors' submissions: approve or send back (`[id]` = one) |

| Teachers (super admin only) | `teachers/` | Ban / unban (a ban by hand is never marked automatic; if Supabase's step fails, a ban that already existed stays), give or take the editor role (`setEditor`). | Safety (super admin only) | `safety/` | Every protection against misuse, with its numbers, in groups that open on a click. The click limits come from the `click_limits` rows (so a changed number shows by itself): "Click limits at a glance" (one table, its "What counts" words in `COUNTS`), Speed limits (a limit with a `<feature>_daily` one shows as one item, its words in `PAIRS`), one "Automatic ban" item, and "Not covered yet" (the gaps: page reloads, a new account after a ban, the login's last hour). Paused teachers now with Release (`releasePause`), with name (`lookUpNames`) and email. History (`safety/history`): every pause, ban and release, 20 at a time (`ShowMore` from the home pages); each row keeps the email, so a deleted account's rows stay ("Account deleted"; `20261213000000_click_history_keeps_email.sql`) for a year: the daily cleanup deletes older rows (`KEEP_SAFETY_RECORDS_DAYS`, `src/lib/cleanupAccounts.ts`; listed as "Old safety records deleted") |

| Admin log (super admin only) | `activity/` | Every admin action from the `admin_actions` table, newest first, 50 a page; filter by admin and action (`?admin=`, `?action=`, `?page=`; the filter is a `next/form` `Form` with `FormPending` inside, so the top line shows even though only the search changes). | Maintenance (super admin only) | `maintenance/` (`page.tsx`, `MaintenanceControls.tsx`, `actions.ts`) | Turn maintenance on / off (asks first with `ConfirmModal`; `setMaintenance` → `set_maintenance`) with an optional note teachers read (zod, `MAINTENANCE_MESSAGE_MAX`), and "Announce ahead" (a time from the computer's clock and the note; `announceMaintenance` → `announce_maintenance`; "Take it away" clears it). | Announcements (super admin only) | `announcements/` (`page.tsx` + `AnnouncementList.tsx`, `new/`, `[id]/`, `AnnouncementForm.tsx`, `AnnouncementTextEditor.tsx`, `actions.ts`) | The list (from `admin_announcements`: status Live / Scheduled / Ended / Off, parts, how many accounts match now, how many closed each part) with Edit, Turn on/off and Delete (asks first). The form: name, on, start / end (Philippine time), the modal's and the bar's text (a Tiptap box: bold, italic, underline, color, align, links; pictures and GIFs in the modal only, uploaded through `/api/announcement-image` (a GIF as it is, 2 MB at most), always centered and resized by dragging a corner handle, or "Full width" (↔, a selected picture fills the modal: `fullWidthSize` makes it 672 wide, and a picture is never wider than its modal)), the modal's Size (Small / Medium / Large width, `MODAL_SIZES`; its text box takes that width, so a picture's size there is its size for teachers) and close delays, show again (once / once a day / every visit), pages, who sees it (gender, age, provinces, town words, education, field words, presentations, role), "Matches about N accounts now" (`countAudience` → `announcement_audience`, half a second after a change) and Preview (the real `AnnouncementModal` / `AnnouncementBar`). Actions check `announcementSchema` (zod) and `isSuperAdmin`, then call the rpc and `forgetMaintenanceStatus` (the status carries the announcements key). How it works: root `CLAUDE.md`, "Announcements" |
| Data check (super admin only) | `data-check/` | "Check saved data": reads every presentation (50 at a time) and review draft with the secret-key client, parses each like the editor opens it (`rowToPresentationInput` + `presentationSchema`, which upgrades old shapes), and lists the ones that fail (slide number, zod's message). Only reads. Works only in development (`NODE_ENV === "development"`): on the live site the page says to run it on your computer and the action refuses. A review draft's row links to its review page when the round is submitted, else to the Under review list. ## How an admin action is written

Each folder's `actions.ts` holds its server actions (`"use server"`). Each one, in this order:

1. Checks the input with zod (`safeParse`), and that `(await getAccount()).isAdmin`.
2. Calls the database (usually an rpc like `publish_review`) with the server client (`createClient()` from
   `@/lib/supabase/server`). Only use `createAdminClient()` for things the database can't do, like Supabase's
   login ban.
3. Calls `refresh()` so the page shows the new data.
   The Admin log needs nothing here: the database writes it (triggers on the tables an admin changes, into
   `admin_actions`), so an action does not log itself. The exceptions are the steps a trigger can't see: ban, unban
   and releasing a pause. Those call the `log_ban`, `log_unban` and `log_click_release` rpcs after the step worked.
4. Returns `null` (worked) or a short message for the user, turning known refusal codes (`QMRVW`, `QMBRV`, …) into
   words. The page shows it in a sonner toast.

Confirmations use `ConfirmModal` (`src/components/editor/ConfirmModal.tsx`), never the browser's `confirm()`.
Reviews and Submissions rules: see the root `CLAUDE.md`. `ReviewDraftView` and `PresentDraftButton`
(`src/components/presentation`) are shared with the reviewer's own pages.
